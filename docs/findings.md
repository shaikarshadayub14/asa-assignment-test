# Security Findings — VulnTracker

Findings are sourced from four automated scans (SAST, SCA, container, IaC — raw JSON in `reports/`) plus manual review of `app/` and `notify/`. Each finding lists the detecting source, a severity with justification specific to this application, the business impact, and whether it lives in starter code or in the Task 1 "Shared Report Link" feature.

VulnTracker stores an organization's unpatched vulnerability inventory — exactly the data an attacker would want before choosing a target. Findings that leak or expose *scan data* are rated more severely here than the same class of bug would be in a generic CRUD app, because the blast radius includes a roadmap of every other weakness in the customer's environment.

## Critical

| # | Finding | Source | Severity & justification | Business impact | Code |
|---|---|---|---|---|---|
| 1 | SQL injection in scan search (`search_scans_by_query` built a query via f-string interpolation) | Manual review | **Critical** — unauthenticated-adjacent (any logged-in user, no additional privilege) SQL injection against the primary datastore | Full read/write access to every user's vulnerability data, credentials table, and share-link tokens via a single authenticated endpoint | Starter code — **fixed** |
| 2 | JWT `alg=none` accepted (`decode_token` allowed `["HS256", "none"]`) | Manual review | **Critical** — lets an attacker forge a valid-looking token for any username with no signature at all | Complete authentication bypass; attacker impersonates any user and reads/edits/deletes their scan data | Starter code — **fixed** |
| 3 | Broken access control on `GET /scans/{scan_id}` — the only scan-read/write route without an `owner_id` filter, unlike `list_scans`, `update_scan`, and `delete_scan` in the same file | Manual review | **Critical** (IDOR / CWE-639) — any authenticated user can enumerate sequential integer IDs to read any other tenant's scan, including `cve_id`, `affected_component`, and `remediation_notes` | Cross-tenant disclosure of exactly which unpatched CVEs affect other customers — directly enables targeting them | Starter code — **not fixed** (see `remediation-plan.md`) |

## High

| # | Finding | Source | Severity & justification | Business impact | Code |
|---|---|---|---|---|---|
| 4 | Hardcoded `SECRET_KEY`, `DB_PASSWORD`, `ADMIN_API_KEY` committed in `config.py` | Manual review | **High** — JWT signing key and DB credentials in source control, present in every clone/fork history | Anyone with repo read access can forge tokens or reach the DB directly, bypassing the app entirely | Starter code — **fixed** (env vars via `python-dotenv`, real values only in `.env`/GH Secrets) |
| 5 | Plaintext password logged on every login attempt (success and failure) | Manual review | **High** — credentials land in application/log-aggregation systems, which typically have far weaker access control than the app itself | Anyone with log access (ops, a compromised logging pipeline, a misconfigured log-shipping destination) recovers user passwords directly | Starter code — **fixed** |
| 6 | Share-link token generated with `random.choice` over `string.ascii_letters + digits` (Mersenne Twister, not CSPRNG) | Manual review | **High** — the token *is* the access control for `GET /share/{token}`; a predictable generator narrows the brute-force search space for an external, unauthenticated endpoint | An external party could feasibly guess or narrow down a valid share link and read a scan meant only for one named stakeholder — directly undermines Task 1's stated purpose | **Task 1 (new feature)** — **fixed** (`secrets.token_urlsafe(32)`) |
| 7 | Open, unauthenticated webhook registration + dispatch in `notify/` (`POST /webhooks` accepts any `url` with no auth; `POST /notify` fires attacker-controlled outbound POSTs to it) | Manual review | **High** (SSRF / open relay, CWE-918) — no authentication anywhere in `notify/src/index.js`; the service will POST JSON to whatever URL is registered | An attacker can register `http://169.254.169.254/...` or an internal-only host as a "webhook" and use the notify service as an SSRF pivot into the network it runs on, or as a DoS amplifier against a third party | Starter code (`notify/` — README states "no changes required") — **not fixed**, documented in `remediation-plan.md` |
| 8 | `cryptography`, `starlette`, `python-multipart` pinned to versions with known HIGH-severity CVEs (denial-of-service and request-smuggling classes; see `reports/sca.pip-audit.json`) | SCA (pip-audit) | **High** — these sit directly on the request-handling path of every API call, not in an optional/dev-only dependency | Availability risk (DoS) and potential request-parsing confusion on an API that security teams rely on to track active vulnerabilities — an outage here delays remediation of everything else | Starter code — **partially fixed**: bumped fastapi/starlette/cryptography/python-multipart/pytest (33→28 findings via pip-audit); no fully-patched release exists yet for the remaining starlette/cryptography advisories |
| 9 | Kubernetes deployment references `vulntracker-api:latest` rather than a pinned digest (`CKV_K8S_14`, `CKV_K8S_43`) | IaC (Checkov) | **High** — `:latest` breaks reproducible deploys and means a compromised or accidentally-overwritten tag on Docker Hub silently changes what's running in production | Supply-chain risk: there's no guarantee the image running in the cluster matches the image that was scanned and reviewed | Task 4 (new infra) — **not fixed**, documented in `remediation-plan.md` |
| 10 | Container base image (`python:3.11.9-slim-bookworm`) carries 12 CRITICAL and 77 HIGH OS-package CVEs, concentrated in `perl-base`, `libssl3`/`openssl`, `libgnutls30`, and `libexpat1` | Container (Trivy) | **High**, not Critical — these are transitively-installed Debian packages (e.g. `perl-base` is a dependency chain artifact, not something the app invokes), so exploitability requires an already-compromised container, not a direct network path. ## Medium

| # | Finding | Source | Severity & justification | Business impact | Code |
|---|---|---|---|---|---|
| 11 | CORS middleware reflects any `Origin` header back with `Access-Control-Allow-Credentials: true` (`main.py` `cors_middleware`) | Manual review | **Medium** — effectively a wildcard-with-credentials CORS policy; auth here uses a Bearer header rather than cookies, which limits (but doesn't eliminate) the practical exploit path | A malicious site loaded by a logged-in user's browser could make authenticated-looking cross-origin requests if the token is ever exposed to JS in a way a script on that page can reach | Starter code — **not fixed**, documented in `remediation-plan.md` |
| 12 | Global exception handler returns the raw exception message, type, and full Python traceback (including file paths) to the client on any unhandled error | Manual review | **Medium** — information disclosure; reveals internal file structure, library versions, and query fragments that ease further attack development | Speeds up an attacker's reconnaissance after triggering any unexpected error; also a poor look for a security-focused product to leak internals to the public | Starter code — **not fixed**, documented in `remediation-plan.md` |
| 13 | No rate limiting or lockout on `GET /share/{token}` password check | Manual review | **Medium** — password-protected share links can be brute-forced online since there's no throttling, though bcrypt's cost factor slows each attempt | Undermines the "optional password protection" guarantee of Task 1 for a link an attacker has already obtained (e.g. via the weak-PRNG issue above, before it was fixed) | **Task 1 (new feature)** — **not fixed**, documented in `remediation-plan.md` |
| 14 | Kubernetes secret delivered via env vars rather than mounted files (`CKV_K8S_35`) | IaC (Checkov) | **Medium** — env vars are more likely to leak via process listings, crash dumps, or child-process inheritance than a file the app must explicitly open | Marginally increases the chance of secret exposure during an incident, but the app already reads config via `os.environ` throughout, so a file-based rework is a real but non-trivial refactor | Task 4 (new infra) — **not fixed**, documented in `remediation-plan.md` |
| 15 | `notify/` dependencies (`axios`, `express`, `body-parser`, `path-to-regexp`, transitively pulled in) carry HIGH-severity `npm audit` advisories, mostly ReDoS/SSRF-adjacent classes | Manual review (supplementary `npm audit`; not one of the 4 required scans, which target `app/`'s Python stack) | **Medium** — `notify/` is explicitly out of scope for changes per the README, and its exposure is already dominated by finding #7 (no auth at all) | Same service already has a more severe unauthenticated-access problem; patching these libraries doesn't address the root exposure | Starter code — **not fixed**, noted for completeness |
